1. 对 10,000 元账户，这套系统最大的价值是"纪律"（止损价、股数、每天只看两张卡），其次才是选股 alpha。所以工程优先级要放在"每天都能稳定出卡"，再放在模型。

### 1.5 冠军回测协议的两处泄漏（C4，2026-10-12）

C4 用冠军同配方的 84 个月末样本外预测（2019-07 ～ 2026-06，`same_protocol_20260922_144648`）复现研究时先撞上协议本身的问题：

- `research/backtest._load_tradability` 用 **qfq 收盘**对比 `limit_price.up_limit`（未复权）。历史越早复权比例越大，涨停封死越检不出来。源码已核对（`backtest.py` 第 41、49 行）。
- `universe.list_date` 为空的比例，协调者独立查询：sh 2,320/2,466、sz 2,904/3,091、bj 349/349。`is_too_new` 在 `list_date is None` 时返回 False，次新过滤实际没生效。

C4 报告：原口径 Top-30 净 CAGR 33.1%，与注册表登记的 33.7% 一致；改用 `daily_basic.close` 对比涨停价、并要求 qfq 历史 ≥ 60 个自然日后，Top-30 CAGR 降到 **9.8%**，Top-10 相对全池等权的超额 +0.26%/月（t=0.45）。2,520 个 Top-30 名额里 118 个（4.7%，均值 +41%/月）是不可买的一字板或次新，其余名额均值 +1.15%/月。协调者没有重跑这 84 期，33.1%→9.8% 以该报告为准；泄漏机制和 `list_date` 空值率是独立核实过的。

在修正口径下，C4 的其余结论：价格上限不损失可测量的 RankIC（子池 0.056–0.058 vs 不限 0.055，Top-N 收益差 p 全部 > 0.1）；控制 log 价格后 RankIC 0.0547→0.0525（差的 p=0.62），五个价格分位内都为正；万元账户现行规则单笔约 1,028 元、只投入约 30%、费用占投入资本 **13.7%/年**，3 个 30% 仓位把费用降到投入资本的 6.0%/年，但收益差不显著（p>0.3）。±8% 止损在月度口径下没有改善任何变体（p 0.30–0.51），证据不足，不改。

建议（依据是费用算术，不是那些不显著的收益差）：开仓候选先按一手成本 ≤ 约 3,000 元过滤；万元账户用 3 个仓、单票约 30%（这要改现在的 15% 单票上限）；最小票面 ≥ 1,700 元，且必须和 30% 仓位一起上，否则 1% 风险预算把单笔卡在 1,250 元、最小票面会让成交笔数为零。

## 2. 逐层评估：优点、缺点、可优化处

### 2.1 产品定位

优点：目标用户（散户、每天 10 分钟）清楚；输出形态（开仓卡/持仓卡 + 明日待办 + 影子仓）是对"纪律"最直接的产品化；不自动下单、不承诺收益的边界守得住。

缺点：
- 规则参数（1% 风险、15% 单票、10% 现金缓冲、100 股整手）是按"几十万账户"设计的，落到 1 万元只剩 ≤12.5 元的股票可买，可买域和模型偏好发生纠缠（见 1.2）。
- 费用模型里 5 元最低佣金没进入卡片决策，用户看不到"这笔交易成本 1%"。
- 建议卡没有"事后回看"：用户无法在应用里看到过去卡片的实际结果。

可优化：
- 以 C4 研究结论为准，确定 10k 账户的仓位数（2–4 只）、最小票面（例如 ≥1,700 元让 5 元佣金 ≤0.3%）和开仓卡价格/一手成本过滤。
- 卡片增加"预计来回成本 x 元（x%）"一行，直接由 `a_share_rules.apply_costs` 计算。
- 实盘表现页（C3）作为固定页面，让用户每周看一次"卡片 vs HS300"。

### 2.2 模型与研究

优点：Walk-Forward + Purged K-Fold 纪律完整；冠军-挑战者同协议门禁已经挡掉了 DL 挑战者和回归树（0.0775 vs 0.0554，四路 p=0.047，未晋升）；预测与建议都有留痕表，可以做实盘回看。

缺点：
- RankIC 0.055 的信号在 5,000 只股票里排 Top-10，单期胜率接近掷硬币，必须依赖止损和多期累积；用户预期需要在手册里对齐。
- 价格水平是未受控的混淆变量：模型可能学到"低价股溢价"而非基本面/量价 alpha。
- bj 池 341 只样本太少，RankIC 0.083 的置信区间很宽；bj@09-17 实盘 RankIC −0.05。

可优化（按冠军-挑战者门禁执行）：
- 在训练特征里加入 log 价格或以价格分层做中性化作为挑战者；验收标准：同协议 WF RankIC 不低于冠军，且残差 RankIC（去价格后）显著高于冠军。
- 建立"实盘 RankIC 月报"：每月末用 `prediction_log` 计算当月全部快照的 10/20 日 RankIC 和残差 RankIC，连续 3 个月残差 RankIC ≤0 则触发重训/重审。

### 2.3 数据更新

优点：断点续跑、`pipeline_state` 假锁清理、启动自检、三重数据源（akshare / sina / eastmoney / tushare）互为备份。

缺点：
- 行情、基本面、公司行动都是逐股 HTTP 循环，5,000+ 次请求 × 若干数据集，是 10 小时级周末链的根源。
- qfq 增量存储存在"除权后旧行不重算"的理论缺陷（C2 工作流用真实分红股核验）。
- bj 池工作日跳过，周末又跑不完，导致 bj 行情停更两周。

可优化：
- 行情换 tushare `daily + adj_factor` 按交易日批量（一天 2 次请求覆盖全市场），验收：200 只抽样 60 个交易日非事件日 99.9% 行内误差 ≤0.1%，且能解释所有系统性偏差。
- 基本面/公司行动改为 tushare 按报告期批量（`fina_indicator_vip`、`dividend`），把 3 秒/只的循环砍掉。
- 周末链目标：≤90 分钟；工作日链：≤20 分钟（含 bj）。

### 2.4 运维模式

优点：计划任务分工清晰（工作日决策、午夜补课、周末研究、影子仓、开机自检）；日志落盘。

缺点：
- 单机依赖开机状态；任务失败只有退出码，之前连日志都没有（今日修复后首次产出日志）。
- `.ps1` 编码、venv 双进程、DuckDB 锁冲突这类"环境问题"过去吃掉了大量调试时间。
- 日志里中文仍是乱码（cmd 重定向用 GBK 写、文件按 UTF-8 读），排障成本高。

可优化：
- 统一 `.ps1` 为 UTF-8 BOM（已完成），包装脚本输出前 `chcp 65001` 或由 Python 端 `PYTHONIOENCODING=utf-8` 写日志。
- 每个计划任务结束时写一行 `data/logs/heartbeat.jsonl`（任务名、开始/结束、退出码、关键数字），应用首页读它显示"昨夜任务是否成功"。
- 中期可把周末研究链搬到低价云主机或 GitHub Actions（只做研究、不接实盘），笔记本只跑 20 分钟的工作日链。

### 2.5 架构

优点：分层边界清晰（见上）；EAV 财务表、单写者、注册表版本化；测试脚本覆盖规则/回测/经纪/引擎。

缺点：
- 测试依赖 `python -m scripts.test_*` 手工执行，没有一键全跑；仓库里没有 pytest。
- 文档很多（60+ 份），缺一份"当前状态入口"（本文承担这一角色）。

可优化：`scripts/run_all_tests.py` 汇总跑所有离线测试，作为每次提交前的闸门。

### 2.6 操作建议（给用户的使用方式）

- 每天收盘后看一次卡片：先看市场天气一句话，再看持仓卡止损价，最后看开仓卡。
- 10k 账户只开 2–4 只，用整手下单，开仓前对照卡片上的"来回成本"行。
- 每周看一次实盘表现页；连续两个月卡片组合跑输 HS300 超过 5 个百分点，就暂停新开仓，等模型复审。
- 影子仓用于验证策略，看 30 日视窗的 8 条策略谁更稳，而非每天盯 NAV。

## 4. 任务自循环（多代理元认知）

**边界（用户给定，不可越）**：不自动下单；不承诺收益；冠军模型只经同协议门禁替换；BJ 池固定 champion_bj；DuckDB 单写者；不提交 `.env`/`*.duckdb`/密钥；`main` 不强推；A 股规则以 `research/a_share_rules.py` 为准。
